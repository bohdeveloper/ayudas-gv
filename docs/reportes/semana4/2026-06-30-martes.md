# Reporte diario — Martes 30/06/2026

## Completado

### `ExpedienteRepository` — SQL dinámico parametrizado

- `NamedParameterJdbcTemplate` (mismo patrón que `UsuarioRepository` de Semana 2), sin JPA
- Método `buscar(criteria, descColumn)`: cada filtro solo se añade al `WHERE` si el usuario lo indicó — nunca se concatena el valor recibido en el SQL, siempre como parámetro nombrado
- Filtros soportados:
  - `numeroExpediente` → `ILIKE` con coincidencia parcial
  - `tipoAyuda` / `estado` → igualdad por código de catálogo
  - `documentoSolicitante` → subconsulta `EXISTS` contra `expediente_interesado` + `persona` filtrando por `rol_interesado = 'SOLICITANTE'`
  - `fechaDesde` / `fechaHasta` → rango sobre `fecha_registro`
- Método `contar(criteria)` reutiliza el mismo `buildWhereClause` para calcular `totalElements` sin duplicar la lógica de filtros
- Columna de descripción de catálogo (`descripcion_es` / `descripcion_eu`) parametrizada en el SQL mediante `String.formatted()` — pero solo a partir de una lista cerrada de dos valores fijos decididos en código Java, nunca desde un dato del cliente, así que no hay riesgo de inyección

### Ordenación segura con lista blanca de columnas

- `SORT_COLUMNS`: mapa cerrado `numeroExpediente → e.numero_expediente`, `fechaRegistro → e.fecha_registro`, `estado → ee.orden`, `tipoAyuda → ta.codigo`
- Cualquier valor de `sort` que no esté en la lista se ignora y se aplica el valor por defecto (`fechaRegistro,desc`) — evita construir un `ORDER BY` con una columna arbitraria del cliente

### `ExpedienteService`

- Normaliza `page`/`size`: página por defecto 0, tamaño por defecto 10, máximo 100 (evita que un cliente pida páginas enormes)
- Resuelve la columna de descripción de catálogo a partir del `Locale` de la petición: `eu` → `descripcion_eu`, cualquier otro caso → `descripcion_es`
- Orquesta `buscar()` + `contar()` del repositorio y construye el `PageResponseDto`

### Compilación y primera prueba

- `mvn compile` en verde tras añadir las tres clases nuevas
