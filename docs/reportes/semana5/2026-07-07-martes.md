# Reporte diario — Martes 07/07/2026

## Completado

### `GET /v1/expedientes/{id}/interesados`

- `ExpedienteRepository.buscarInteresados(id)`: una sola consulta a `expediente_interesado JOIN persona`, clasificada en Java por `rol_interesado` (`SOLICITANTE` → objeto único, `REPRESENTANTE` → objeto único opcional, `CAUSANTE` → lista)
- `ExpedienteRepository.existeExpediente(id)` (`SELECT EXISTS(...)`) — se usa en las tres secciones que no tienen una fila "cabecera" propia (interesados, contacto, ayuda) para poder distinguir "expediente inexistente" (404 genérico) de "sección vacía" antes de construir la respuesta
- `ExpedienteService.obtenerInteresados(id)` comprueba existencia y delega en el repositorio; el controlador expone `GET /{id}/interesados`

### `GET /v1/expedientes/{id}/contacto`

- `ExpedienteRepository.buscarContacto(id)` — `datos_contacto` es una relación 1:1 *opcional* con `expediente` (columna `uq_dc_exp` única pero sin `NOT NULL` forzando su existencia), así que se modela como `Optional<SeccionContactoDto>`
- Si el expediente existe pero no tiene fila de contacto, se lanza `RecursoNoEncontradoException` con un mensaje específico ("no tiene datos de contacto registrados"), distinto del 404 genérico de expediente inexistente — mismo `ErrorResponse`, mensaje más útil para depurar
